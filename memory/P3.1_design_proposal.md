# MEELORA V2 — PHASE 3 / P3.1 — PROPOSITION D'ARCHITECTURE (DESIGN ONLY)
> Statut : **PROPOSITION — EN ATTENTE D'APPROBATION**. Aucune implémentation, aucune collection, aucune migration, aucun changement legacy. Base : Financial Core Phase 2 (P2.1→P2.10) clos et stable.

---

## 1. Architecture globale du moteur de reporting
Pipeline sémantique **additif** et strictement en **lecture** au-dessus du Financial Core (jamais d'écriture dans les collections P2) :

```
accounts (P2.3)                         ← identité comptable opaque (code string, devise, normal_balance)
      │  account_mappings (N→1 canonique)
      ▼
financial_concepts (canoniques, neutres juridiction)   ← SENS financier
      │  reporting_template_lines référencent des concepts (pas des comptes)
      ▼
reporting_templates (sections / lines / formules)       ← PRÉSENTATION (par juridiction ou custom)
      │
      ▼
reporting_engine (calcul à la demande, read-only sur trial_balance_lines / journal via P2.8)
      │
      ▼
report_runs (snapshots immuables)                        ← REPRODUCTIBILITÉ / AUDIT
```

Principes directeurs :
- **Séparation stricte sens ≠ présentation.** Le compte ne connaît jamais « ligne 4 du P&L canadien ». Le concept porte le sens ; le template porte la mise en forme.
- **Additif & non destructif.** Aucune écriture P2, aucune modification `acct_*`/`qc9434_*`. Le moteur consomme les données via la couche de compatibilité P2.8 (`financial_data_source`) et la logique P2.5/P2.6.
- **Déterministe & reproductible.** Un rapport émis fige (template_version, snapshot de mappings, import_ids sources, valeurs calculées) → jamais altéré rétroactivement.
- **Multi-juridiction & multilingue par conception**, extensible par industrie sans redesign du noyau.
- **Le moteur de calcul lui-même n'est PAS conçu dans P3.1** (il vient en P3.4). P3.1 pose uniquement la couche sémantique + templates + mappings + reproductibilité.

## 3. Stratégie de hiérarchie des concepts
- **La hiérarchie appartient d'abord aux concepts** (arbre canonique, faible profondeur, via `parent_concept_id`) car elle porte le **sens** stable et sert P&L, Bilan, Cash Flow **et** KPI de façon uniforme.
- **La présentation hiérarchique (sous-totaux, ordre, regroupements d'affichage) appartient aux templates.** Un même concept peut apparaître à des endroits/regroupements différents selon la juridiction sans changer le concept.
- **Donc : hiérarchie dans les deux, mais rôles distincts** — concepts = taxonomie sémantique ; templates = arbre de présentation. On évite la sur-complexité en gardant l'arbre concept peu profond (≤3 niveaux) et en poussant toute cosmétique dans les templates.
- Les concepts « contra » (amortissements cumulés) sont modélisés explicitement pour un signe de présentation correct.

## 4. Schéma `financial_concepts` (proposé)
```
financial_concepts
  _id                 "fc_<uuid>"            (code interne technique)
  concept_code        "CASH_AND_CASH_EQUIVALENTS"   (unique, langue-neutre, stable)
  parent_concept_id   "fc_..." | null
  concept_type        "asset|liability|equity|income|expense|contra_asset|contra_liability"
  statement_type      "balance_sheet|income_statement" (classement primaire)
  natural_balance     "debit|credit"        (sens naturel attendu)
  cash_flow_category  "operating|investing|financing|none"   (défaut, override possible)
  level               int                    (profondeur dérivée, aide au rendu)
  sort_order          int
  is_aggregate        bool                   (concept parent non mappable directement)
  scope               "system"               (concepts standard = gérés système)
  version             int
  status              "active|deprecated"
  labels_i18n         { "en": "...", "fr": "...", "de": "...", "it": "..." }  (ou table séparée, voir §17)
  tags                ["kpi:current_assets", ...]  (extensibilité KPI/industrie)
  created_at / updated_at
```
- Concepts standard = **scope=system** (aucun `workspace_id`), versionnés, non supprimables (deprecate only).
- `is_aggregate=true` ⇒ non mappable par un compte (ex. `ASSETS`, `OPERATING_EXPENSE`) — sert d'agrégat de template/KPI.

## 5. Schéma `account_mappings` (proposé)
```
account_mappings
  _id                  "acm_<uuid>"
  workspace_id         (tenant)              ← client-scoped, jamais system
  company_id
  account_id           → accounts._id (P2.3)  (jamais l'account_code muté)
  financial_concept_id → financial_concepts._id
  weight               float  default 1.0     (préparé pour splits futurs ; =1.0 en mode canonique)
  effective_from       ISO date               (versioning temporel)
  effective_to         ISO date | null
  source               "manual|excel|api|legacy|rule|suggested"
  confidence           float | null           (0..1 ; utile pour suggestions futures)
  status               "unmapped|suggested|confirmed|rejected"
  suggested_concept_id "fc_..." | null         (proposition en attente de revue)
  superseded           bool default false      (jamais de suppression physique)
  superseded_by        "acm_..." | null
  created_by / created_at / confirmed_by / confirmed_at
```
- **Jamais de suppression** ; changement = nouvelle version (effective window) + `superseded`.
- `unmapped` peut être matérialisé (placeholder) ou dérivé (compte sans mapping confirmé) — décision §30.

## 6. Décision de cardinalité du mapping
- **Défaut fort : 1 compte → 1 concept canonique confirmé** par fenêtre effective (contrainte d'unicité sur mapping `confirmed` actif par `account_id`). C'est la règle pour tout reporting comptable standard.
- **Extensibilité conçue, non implémentée** : le champ `weight` + l'absence de contrainte « stricte 1:1 au niveau schéma » permettent d'introduire plus tard des mappings d'allocation/split (un compte réparti sur plusieurs concepts, somme des poids = 1.0) **sans changer le schéma**. P3.1 ne l'active pas (validation applicative : un seul `confirmed` par compte).

## 7. Workflow de gouvernance des mappings
Machine à états (attribut `status`) :
```
unmapped ──(proposer)──► suggested ──(confirmer)──► confirmed
    ▲                        │                          │
    │                    (rejeter)                  (remplacer)
    └────────────────────► rejected            ► nouvelle version confirmed (supersession)
```
- `suggested` : produit à terme par un moteur d'auto-mapping (**non implémenté en P3.1** ; seul le modèle de données/champs `suggested_concept_id`/`confidence` est posé).
- `confirmed` : seul état pris en compte par le moteur de reporting.
- `rejected` : conserve la trace (audit) ; ne bloque pas une future suggestion différente.
- **Complétude de mapping** = indicateur de préparation reporting (analogue à `cutover_ready` P2.9) : % de comptes actifs à solde non nul disposant d'un mapping `confirmed`.

## 9. Stratégie d'intégration — Canada
- Profil `jp_CA` : référentiels SME (p.ex. présentation type ASPE PME) branchés via **templates standard** référençant les concepts canoniques.
- Aucun plan comptable canadien codé en dur ; la correspondance se fait par `account_mappings` (compte client → concept). Le template canadien décrit l'ordre/sous-totaux/terminologie (« Chiffre d'affaires », « Bénéfice net »).
- Support futur d'autres référentiels (IFRS) = template supplémentaire, mêmes concepts.

## 10. Stratégie d'intégration — Suisse
- Profil `jp_CH` : présentation selon le **Code des obligations (art. 957 ss / 959 ss)** — structure minimale du bilan et du compte de résultat, réserves légales, etc., exprimée comme **template standard**.
- Concepts canoniques identiques (ex. `RESERVES`, `SHARE_CAPITAL`, `FINANCIAL_EXPENSE`) ; seule la présentation + terminologie (de/it/fr) diffèrent.
- Le même compte mappé à `CASH_AND_CASH_EQUIVALENTS` alimente aussi bien le template CA que CH → **preuve de la neutralité de juridiction**.

```
reporting_templates
```

## 12. Sections / lignes / formules
```
reporting_template_lines
  _id              "rtl_<uuid>"
  template_id      "rt_..."           (appartient à une VERSION de template)
  parent_line_id   "rtl_..." | null   (arbre de présentation)
  line_code        "REVENUE" | "GROSS_PROFIT" | ...
  line_type        "section | concept | subtotal | formula | spacer"
  concept_refs     ["fc_...", ...]    (pour line_type=concept : concepts agrégés)
  formula          "REVENUE - COST_OF_GOODS_SOLD"  (pour subtotal/formula : réf. line_code)
  display_sign     "natural | positive | negative | inverted"   (voir §18)
  measure          "period | ytd"     (quelle mesure P2.5 utiliser)
  labels_i18n      { ... }
  sort_order       int
  is_bold / indent_level / show_if_zero ...
```
Exemple (P&L) :
```
REVENUE (subtotal)      = Σ concepts(OPERATING_REVENUE, OTHER_OPERATING_INCOME)
COST_OF_SALES (concept) = concept(COST_OF_GOODS_SOLD)
GROSS_PROFIT (formula)  = REVENUE - COST_OF_SALES
```
- **Le moteur de calcul n'est PAS implémenté en P3.1** : on définit la grammaire (références concepts, formules par `line_code`, mesure period/ytd, signe). Le calcul effectif = P3.4.
- Formules limitées à `+ - ()` et références de `line_code` internes au template (déterministe, pas de code arbitraire).

## 13. Architecture des templates custom
- Un template custom est un `reporting_templates` de `scope=workspace|company`, **versionné**, dérivable d'un standard (`based_on_template_id`).
- **Préférence forte : lignes custom → concepts** (préserve la sémantique, KPIs/Cash Flow restent alimentés). L'upload d'un P&L/Bilan client se traduit en lignes référençant des concepts.
- **Exception documentée : mapping direct compte → ligne** autorisé UNIQUEMENT quand un compte client n'a pas de concept canonique adéquat (cas résiduel). Modélisé par un champ optionnel `account_refs` sur la ligne, marqué `semantic_bypass=true` pour audit/alerte. À éviter ; jamais le défaut.
- Upload d'un nouveau template = **nouvelle version** ; ne détruit jamais les définitions historiques.

## 14. Versioning des templates
- Templates **immuables une fois `published`** ; toute modification crée `version = n+1` (nouveau lot de lignes). Statuts `draft → published → archived`.
- Les `report_runs` référencent une `template_version` précise ⇒ un rapport reste reproductible même si le template évolue.

## 15. Versioning des `account_mappings`
- Versioning temporel par `effective_from`/`effective_to` + `superseded` (jamais de delete). À une date donnée, l'ensemble des mappings `confirmed` actifs est déterministe.

## 16. Reproductibilité des rapports historiques
```
report_runs
  _id                 "rr_<uuid>"
  workspace_id / company_id / financial_period_id
  template_id / template_version
  statement_type / measure
  source              "legacy|normalized"   (via financial_data_source P2.8 au moment du run)
  source_import_ids   { trial_balance: "imp_...", journal: "imp_..." }
  mapping_snapshot    [ {account_id, concept_id, weight} ... ]  (gel des mappings confirmés utilisés)
  computed_lines      [ {line_code, value, ...} ]   (résultat figé)
  concepts_version_snapshot / jurisdiction / locale
  generated_by / generated_at
  status              "final"   (évidence, non supprimable)
```
- Un rapport figé = **jamais** recalculé silencieusement. Reproduire = rejouer avec les snapshots stockés.

## 17. Architecture multilingue / localisation
- **Codes internes langue-neutres** (`concept_code`, `line_code`, `template_code`) — jamais traduits.
- Deux options (décision §30) : (a) champ `labels_i18n` embarqué (JSON par locale) — simple ; (b) table dédiée `i18n_labels(entity_type, entity_id, locale, label)` — plus scalable/gouvernable. **Recommandation : (b)** pour concepts/templates système (gestion centralisée, ajout de langue sans migration de doc), (a) toléré pour labels custom rapides.
- Locales cibles : `fr`, `en` (min.) ; `de`, `it` pour CH. Fallback déterministe (locale demandée → locale par défaut du profil → `en`).

## 18. Convention de signe de présentation
- **Le Financial Core reste intact** : `net = debit − credit` (P2.5), jamais muté.
- La **présentation** ajoute une règle de signe **au niveau ligne de template** (`display_sign`) et/ou dérivée du `concept_type`/`natural_balance` : ex. les produits (natural credit, net négatif) s'affichent en positif dans le P&L.
- Règle par défaut par `concept_type` (income → afficher positif, expense → positif en tant que charge, contra → inversé), surchargée si besoin par ligne. **Où ça vit : couche présentation (concept_type default + template line override).** Jamais dans accounts/TB.

## 19. Stratégie d'extensibilité Cash Flow
- **Classification `operating|investing|financing` = attribut**, pas une branche de la taxonomie.
- Recommandation : **défaut au niveau concept** (`cash_flow_category`) + **override possible au niveau mapping** (rare) et **structuration au niveau template Cash Flow** (P3.x). Les ajustements indirects (variations de BFR, D&A) seront des **règles de template Cash Flow** consommant les concepts.
- Donc : concepts portent le défaut ; le template Cash Flow porte la construction (méthode indirecte). **Rien n'est implémenté en P3.1** — seul l'attribut `cash_flow_category` est posé sur les concepts.

## 20. Stratégie d'extensibilité KPI
- Futur `kpi_definitions` (P3.x) : chaque KPI = formule sur des **concepts/agrégats** (jamais sur des `account_code`). Ex. `gross_margin = GROSS_PROFIT / REVENUE`.
- P3.1 garantit que les concepts sont **sémantiquement stables** et taggables (`tags: ["kpi:current_assets"]`) ⇒ current/quick ratio, working capital, DSO, EBITDA margin, debt ratio calculables sans dépendre des codes de comptes.
- **Aucun calcul KPI en P3.1.**

## 21. Stratégie d'extensibilité par industrie
- Futur `industry_profiles` : ajoutent (a) des **concepts d'extension sous parents canoniques** (jamais de nouvelle racine), (b) des **jeux de KPI** spécifiques (SaaS/retail/manufacturing/services/real estate), (c) des **variantes de template**.
- Contrat : les extensions n'altèrent jamais la taxonomie de base ni les mappings existants (rétro-compatibilité garantie par `parent_concept_id` + `version`).

## 23. Index proposés (à créer lors de l'implémentation, pas maintenant)
- `financial_concepts` : unique `(concept_code, version)` ; `(statement_type, sort_order)` ; `(parent_concept_id)`.
- `account_mappings` : `(workspace_id, company_id, account_id, status)` ; unique partiel `(workspace_id, company_id, account_id)` où `status=confirmed AND superseded=false` ; `(workspace_id, company_id, financial_concept_id)`.
- `reporting_templates` : unique `(template_code, version)` ; `(scope, workspace_id, company_id, statement_type)`.
- `reporting_template_lines` : `(template_id, sort_order)` ; `(template_id, parent_line_id)`.
- `report_runs` : `(workspace_id, company_id, financial_period_id, statement_type, generated_at)`.

## 24. APIs proposées pour l'implémentation future (non créées en P3.1)
Lecture référentiel : `GET /api/financial-concepts`, `GET /api/jurisdiction-profiles`, `GET /api/reporting-templates?jurisdiction=&statement_type=`.
Mappings : `GET/POST/PATCH /api/companies/{id}/account-mappings`, `GET /api/companies/{id}/mapping-coverage`, `POST .../account-mappings/{id}/confirm|reject`.
Templates custom : `POST/GET/PATCH /api/companies/{id}/reporting-templates`, versioning `POST .../{tid}/publish`.
Reporting (P3.4) : `POST /api/companies/{id}/reports/{statement_type}` (run), `GET /api/companies/{id}/report-runs`, `GET .../report-runs/{rr_id}`.

## 25. Impact migration / compatibilité
- **100 % additif.** Aucune modification des collections P2 (`accounts`, `financial_years`, `financial_periods`, `data_imports`, `trial_balance_lines`, `journal_entries`, `journal_entry_lines`, `financial_config`, `phase2_signoffs`) ni de `acct_*`/`qc9434_*`.
- Les **rapports legacy restent inchangés** (P&L/Bilan/Flux legacy continuent de fonctionner tant que P3.4 n'est pas activé par société).
- Coexistence avec P2.8 : le moteur lit la source (`legacy|normalized`) via `financial_data_source`. Un futur seed produit `financial_concepts`/`jurisdiction_profiles`/templates standard système (idempotent).

## 26. Risques & questions ouvertes
1. Granularité de la taxonomie (assez fine pour KPI vs. simple pour PME).
2. Politique `unmapped` : matérialisé vs. dérivé.
3. Placement définitif des labels i18n (embarqué vs. table dédiée).
4. Splits/allocations : confirmer qu'ils restent hors P3.1 (schéma prêt, logique différée).
5. Cash Flow indirect : niveau de détail des règles (P3.x).
6. Custom template : gouvernance de l'exception « mapping direct compte→ligne ».
7. Réconciliation « somme des concepts = TB » (contrôle d'intégrité) — à intégrer au moteur (P3.4).
8. Comptes contra (amortissements cumulés) : concepts dédiés vs. signe — proposé concepts dédiés.

## 27. Subdivision recommandée de la Phase 3 (après P3.1)
- **P3.1** Couche sémantique (concepts + mappings + jurisdiction profiles + modèle templates + reproductibilité) — DESIGN puis implémentation après approbation.
- **P3.2** Seed des concepts canoniques + profils CA/CH + templates standard (système, versionnés, i18n).
- **P3.3** Gouvernance des mappings (CRUD, confirm/reject, coverage) — sans IA.
- **P3.4** Moteur de calcul (P&L + Bilan) + `report_runs` + contrôle d'intégrité concepts↔TB.
- **P3.5** Templates custom (upload, versioning, publication).
- **P3.6** Cash Flow (méthode indirecte).
- **P3.7** Comparatifs & management reporting.
- **P3.8** KPI / ratios.
- **P3.9** Dashboards.
- **P3.10** Auto-suggestion de mappings (IA) + extensions industrie.

## 28. Ce que P3.1 IMPLÉMENTERAIT (après approbation)
- Collections + modèles : `financial_concepts`, `account_mappings`, `jurisdiction_profiles`, `reporting_templates`, `reporting_template_lines`, `report_runs` (schéma/indexes seulement).
- Modules service (lecture/écriture de base) + validations de gouvernance (statuts, unicité 1 concept confirmé/compte, versioning/supersession).
- Sécurité P1.12 câblée ; APIs de référentiel + mappings + squelette templates.
- Suite de tests in-memory permanente (paradigme `test_p3_1_*`), smoke live, sans toucher P2.

## 29. Ce que P3.1 N'IMPLÉMENTERAIT PAS
- Aucun **moteur de calcul** de rapport (P3.4).
- Aucun **seed** de taxonomie/templates réels (P3.2) au-delà d'un minimum de test.
- Aucune **auto-suggestion IA** (P3.10).
- Aucun **Cash Flow / KPI / dashboard / comparatif** (P3.6–P3.9).
- Aucune **allocation/split** active.
- Aucun **cutover**, aucune modification P2/legacy, aucune migration de données.

## 30. Points de décision nécessitant approbation client
a. **Granularité finale de la taxonomie** des concepts (valider/ajuster la liste §2).
b. **Cardinalité** : confirmer « 1 concept canonique confirmé par compte » comme règle, splits différés.
c. **Localisation** : labels embarqués (a) vs. table i18n dédiée (b) — recommandation (b).
